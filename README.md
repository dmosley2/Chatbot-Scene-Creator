# chatbotSceneCreator

A locally-run, multi-character AI scene generator inspired by "AI Sponge" — LLM-driven characters (Ryuji, Joker, and Morgana from *Persona 5 Royal*) interact autonomously in dynamically generated scenes, streamed live to a React frontend.

No cloud APIs, no API keys — the entire pipeline (dialogue generation, scene direction, pacing) runs against a local LLM via [Ollama](https://ollama.com).

## What it does

1. Randomly selects a cast of characters and generates a scene premise via LLM
2. An LLM-driven "director" agent selects who speaks next each turn, based on the live transcript and character context — not simple round-robin
3. Each character responds in their own voice, generated by the same underlying model but distinctly prompted
4. Dialogue paces itself toward a natural resolution as the scene progresses
5. Turns stream to the frontend in real time over WebSocket as they're generated

## Architecture

```
Ollama (local LLM)
      ↕ async HTTP
FastAPI backend
      ↕ WebSocket (streaming) + REST + static file serving
React frontend (Vite)
```

- **`app/`** — FastAPI backend: scene orchestration, LLM client, director logic, character loading
- **`personas/`** — Character definitions as JSON (system prompt, model, portrait) — new characters require no code changes
- **`scripts/`** — One-time utility to auto-generate short character summaries (used by the director) from each persona's full system prompt
- **`frontend/`** — React (Vite) client, connects via WebSocket for live scene playback

### Core mechanic: one model, many characters

Each character's dialogue is generated by the same local LLM, distinguished entirely by system prompt and a message-role-flipping technique: from any character's point of view, their own past lines are tagged `assistant` and everyone else's are tagged `user` — letting one model coherently maintain several distinct personalities in a shared conversation.

## Running it

**Requirements:** Python 3.11+, Node.js, [Ollama](https://ollama.com) installed with a local model pulled (e.g. `ollama pull gemma4:e4b`)

```bash
# Backend
python -m venv venv
venv\Scripts\activate      # Windows
pip install -r requirements.txt
uvicorn app.main:app --reload

# Frontend (separate terminal)
cd frontend
npm install
npm run dev
```

Open `http://localhost:5173`.

## Technical challenges

**LLM turn-selection bias.** An early version of the "director" (a second LLM call choosing who speaks next) consistently picked the most recently active character, regardless of conversational relevance — a shallow heuristic from an underspecified prompt. Fixed by giving the director explicit, weighted criteria (direct address > organic relevance > fairness), then iterating further after discovering the fix caused a *different* character to be starved of turns entirely — resolved with a concrete fairness threshold instead of a vague one.

**Scaling scene resolution without hardcoding.** Getting scenes to organically resolve (rather than loop in circular argument) required injecting turn-position-aware pacing instructions. The first attempt used vague language ("wrap up the scene"), which characters largely ignored. A stronger version — offering generic resolution behaviors (concede, compromise, or commit) filtered through "your own personality" — worked without requiring per-character hardcoded resolution logic, preserving the system's data-driven extensibility.

**Duplicate WebSocket connections in React dev mode.** React's StrictMode double-invokes effects in development, which was silently opening two competing WebSocket connections per page load — one of which the backend would try to write to after the browser had already discarded it, crashing mid-scene. Diagnosed via server-side tracebacks (`WebSocketDisconnect`) cross-referenced with duplicate `connection open` log lines, and fixed with a proper `useEffect` cleanup function to close the stale connection before a new one opens.
